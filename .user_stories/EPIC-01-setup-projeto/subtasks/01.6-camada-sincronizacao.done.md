## Passos

- [x] Pull incremental por `updated_at` — `src/lib/sync/pull.ts`. `updated_at` é posto por trigger
      com o relógio do servidor (`supabase/migrations/20260929090000_sync.sql`), e o cursor fica
      na tabela `meta`. Paginação por keyset `(updated_at, id)` em páginas de 500. Cada pull relê
      os últimos 5 min, porque `now()` é a hora de início da transação. Remoções chegam como
      tombstones (`deleted_at` em `saved_items`, `journeys`, `downloads`). Linhas com escritas
      locais ainda por enviar não são sobrescritas.
- [x] Push da `outbox` com idempotency key — `src/lib/sync/push.ts`. A chave é o UUID da linha,
      gerado no cliente: insert = `upsert` (em `saved_items`/`downloads` pela chave natural
      `user_id, item_type, item_id`, para o mesmo item guardado em dois dispositivos ser uma só
      linha); `journey_events` = `on conflict do nothing`; update = patch; remoção = tombstone.
      Repetir qualquer entrada dá o mesmo resultado. A escrita local e a entrada na outbox são
      uma só transação SQLite (`enqueue`).
- [x] Resolução de conflitos: patch por campo, ganha a última sincronização (ver decisão acima);
      `journey_events` append-only (só insert).
- [x] Retry com backoff exponencial — `src/lib/sync/engine.ts`: 2 s × 2^n com jitter (50–100 %),
      máx. 5 min. Um erro de rede pára o push e mantém a ordem; uma recusa definitiva do servidor
      (4xx) fica como dead letter (`failed_at`) e não bloqueia as seguintes. Os ciclos correm um de
      cada vez.
- [x] Escuta de `NetInfo` — `src/lib/sync/use-sync.ts` (montado no layout raiz): a rede de volta
      cancela o backoff e sincroniza logo; também sincroniza no arranque, ao voltar a foreground e
      quando entra um utilizador.
- [x] Indicador global de estado de sync — a sync store ganhou `failedCount`, `lastError` e
      `deriveSyncStatus` (offline, a sincronizar, erro, pendente, sincronizado). O separador Perfil
      mostra um badge (número de pendentes, ou "!" em erro), e o ecrã do Perfil mostra uma linha de
      estado (`src/components/sync-status.tsx`). O aspeto é provisório até ao EPIC-02.
- [x] Aplicar `20260929090000_sync.sql` no projeto (`supabase db push`, 2026-09-29).

## Notas

- **Achados da revisão (2026-09-29), corrigidos:**
  - offline, o ciclo saía antes de atualizar os contadores, por isso o badge não mostrava as
    escritas feitas sem rede como pendentes;
  - sem sessão, a limpeza apagava também os dados do modo de demonstração (`PREVIEW_USER_ID`);
    agora só são apagados quando entra um utilizador real.

- **SQL direto em vez do Drizzle no lado da sync:** o driver do Drizzle para expo-sqlite só tem
  transações síncronas, e cada passo da sync faz `await`. `SqlExecutor` (`src/lib/sync/sql.ts`)
  usa `withExclusiveTransactionAsync` na app e `node:sqlite` nos testes.
- **Remoções do catálogo** não chegam ao dispositivo (o catálogo não tem tombstones). Rever com o
  EPIC-18 (downloads).
- **Dead letters** contam no estado, mas não há UI para as rever nesta fase.
- **Bases de dados de desenvolvimento antigas** ainda têm a rota de demonstração com os ids
  antigos; apagar os dados da app resolve.
